A Kalman filter in hardware

Fall 2026 · West Lafayette, Indiana

This semester the team is building a RISC-V system on chip on an FPGA: an RV32I core with the multiply extension, an on-chip bus of our own, SRAM, a UART back to a host, an SPI controller that reads a six axis inertial sensor, and an accelerator that turns gyro and accelerometer samples into an attitude quaternion without the CPU touching the math. The question the chip exists to answer is what moving the filter into hardware buys, in cycles, power and area, against running it in software on the same core.

My block is the SPI controller that reads the sensor. The team works so that every member knows every part, so this page walks the whole chip, and it is honest about which numbers are design budgets rather than measurements. Nothing here has been measured on silicon yet.

Watch a Kalman filter work

A gyroscope tells you how fast you are turning, so integrating it gives an angle, but it has a bias and the integral drifts. An accelerometer tells you which way is down, so it gives an angle directly, but it is noisy and any time you actually accelerate it lies. A Kalman filter keeps a running estimate of the angle and the gyro bias with a covariance saying how sure it is, predicts with the gyro, corrects with the accelerometer, and weights the correction by how much each side deserves to be trusted. This is the one axis version of what the accelerator computes in three.

Grey is the truth. Amber integrates the gyro alone and walks away. Cyan is the accelerometer alone. Green is the filter, with the bias it has learned in the lower plot. Shake it to see why the accelerometer needs a gate.

The gate is the cheapest line in the whole design and the most valuable. An accelerometer measures specific force, not gravity, so when the board is being pushed the measurement is not pointing down and the update would actively corrupt the attitude. Comparing the vector's magnitude against one g and skipping the update when it is off costs one compare per sample. In the accelerator it is an opcode.

Seven numbers, six errors, twenty one covariances

The real filter estimates a unit quaternion and three gyro biases. A quaternion has four numbers but only three degrees of freedom, so filtering it directly makes the covariance singular. The design keeps the quaternion as a nominal state that is never filtered, and runs the Kalman filter on a six element error state, three small angles and three bias errors, injecting the correction back into the quaternion by multiplication rather than addition. That is the multiplicative extended Kalman filter, and it is why the covariance is 6 by 6 rather than 7 by 7.

Six by six is 36 words, but the matrix is symmetric, so the accelerator stores 21 and addresses them through a packed triangular index: a six entry row offset table plus one addition, no multiplier. Hover the matrix.

The other structural saving is the update. Because the three accelerometer axes are independent, the measurement noise matrix is diagonal, and a diagonal noise matrix means the three measurements can be folded in one at a time. Each scalar update needs a reciprocal, not a matrix inverse, so there is no matrix inverse anywhere in the design. The reciprocal and the inverse square root that normalizes the quaternion both come from Newton-Raphson iterations that borrow the one multiplier.

A straight line of descriptors over one multiplier

The accelerator is not a small CPU. It runs a fixed program of descriptors, fetched from a ROM once per filter step, with no branches. Each descriptor names an operation, two source banks with base addresses and strides, a destination, loop bounds for four hardware loop counters, and a shift to apply on writeback. An address generator walks the loops one product per cycle into a 16 by 16 multiplier with a 48 bit accumulator. A matrix multiply is one descriptor. The whole extended Kalman filter step is about 35 of them.

Simplified address generation: reads from bank A in amber and bank B in cyan, the accumulating destination in green. Triangular destinations skip the lower half, which is where the 21 of 36 saving lives.

The reason a descriptor machine beats a general processor here is that every loop count and every stride is known at design time. The state is six long, the measurement three, the quaternion four, so the program is the same every step and the counters can be hardware. What it costs is placement discipline: each scratchpad is a single port block RAM, so a descriptor can read at most two distinct banks for its operands, and the microprogram is arranged so that the accumulating operations find their operands in the two port register files.

Sixteen bits is not enough for everything

The datapath is 16 bit fixed point. That is plenty for a quaternion and for sensor samples. It is not plenty for the covariance, and the reason is a number the design has to face before the multiplier width is frozen: the process noise added each step is about seven decades smaller than the steady state covariance it is added to. Sixteen bits hold under five decades. Put both in one format and the process noise lands below the least significant bit, the addition does nothing, the covariance shrinks every step, the gain goes to zero, and the filter stops listening to the accelerometer while looking perfectly healthy. The covariance is 32 bit for that reason, and the descriptor format carries separate wide flags for each operand so a wide covariance can multiply a narrow vector.

Design arithmetic from the sensor's rate noise density at a 1 kHz sample rate. Where the process noise lands relative to each word's least significant bit is the whole argument.

The second fixed point trap is rounding. Truncation always rounds the same way, so its error accumulates in proportion to the number of steps rather than its square root, and a slow rotation can round back to zero every step so the attitude never moves and the bias becomes unobservable. The design rounds to nearest and adds first order error feedback on the quaternion writeback. Try a small increment repeated many times under each rule.

The chip around it

The CPU runs a C program compiled for RISC-V. It configures the sensor over SPI, reads samples as they arrive, hands them to the accelerator through memory mapped registers, and streams the quaternion and bias out over UART to a host that compares them against a golden model. The same program with the filter in software gives the baseline the accelerator is measured against: cycle count per sample, and the power and area the block costs on the FPGA.

The sensor is a six axis part rather than a nine axis one, and that was a decision rather than a default. Its noise is documented, which makes synthetic test data tractable; one device keeps the SPI controller to a single peripheral; and a magnetometer's zero gauss offset of around one gauss would swamp the heading over long timesteps for no gain in the quantity we are validating.

My block: the SPI controller

SPI is a four wire synchronous bus, and the whole design question for a controller is the two bits that define its mode: which clock level is idle and which edge samples data. The sensor uses mode 3, clock idle high and data sampled on the rising edge. The first thing that runs on real hardware is a read of the sensor's identity register, because one transaction proves wiring, polarity, bit order and chip select together. Pick a mode and read the byte off the wires.

The thread back to the satellite work is direct. Last summer the firmware read a nine axis IMU over I2C and ran quaternion attitude control in C on a microcontroller, and I verified the actuator protocol by decoding bytes on the wire against an independent implementation. Now the sensor read is a hardware block, verified the same way against a bus functional model of the sensor, one layer down.

Where it stands

Written: the accelerator RTL as a set of modules, the sequencer, address generator, multiply accumulate, Newton-Raphson divide unit, register files, scratchpads, bus interface and top level state machine; the microprogram; the specification these pages summarize; an assumption register that lists every assumption in the design with how to check it; and a verification plan for the UART, the SPI controller and the accelerator, written before the RTL so the RTL had something to be wrong against. Not yet: the measured comparison. Cycle, power and area numbers on this page are budgets from the spec, and they will be replaced by measurements when the chip runs.
